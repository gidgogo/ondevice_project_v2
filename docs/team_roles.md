# 온디바이스 저조도 이미지 복원 프로젝트
## 중간발표 준비 및 5인 역할 분담

2026-10-23 갱신. 기준: LOL-v2-real 학습 620 / 검증 69 / 시험 100, 세 모델 모두 random 180×180 crop, 규칙 기반 선택기, Oracle 제외.

작업 순서·선행 조건·완료 상태는 [실행 계획표](https://github.com/gidgogo/ondevice_project_v2/blob/main/docs/execution_plan.md), 코드 변경 내용은 [변경 이력](https://github.com/gidgogo/ondevice_project_v2/blob/main/CHANGELOG.md)에서 확인합니다. 코드가 준비됐다는 것과 학습 결과가 확보됐다는 것은 구분합니다.

이번 실행은 Colab의 `gt_random_v1` 실험이다. 기존 center 결과는 예비 실험으로 보존한다. 실행 담당자는 [GitHub 팀 실행 안내](https://github.com/gidgogo/ondevice_project_v2/blob/main/colab/README.md)를 따른다.

## 1. 이번 중간발표의 목표

요구된 발표 내용은 다음과 같습니다.

1. **프로젝트 설명 요약 1~2장**: 무엇을 만들고, 왜 지식 증류와 모델 선택을 적용하려는지 설명합니다.
2. **제안한 문제가 실제로 발생하는지 확인**: 직접 측정한 결과와 이미지 사례로 보여줍니다.
3. **중간 진행 결과**: 완료한 평가와 예비실험, 아직 검증하지 못한 내용을 구분합니다.

이번 주 필수 목표는 아래 네 가지입니다.

- [ ] 베이스라인의 이미지별 PSNR·SSIM과 전체 평균 확보
- [ ] 동일한 CPU 환경에서 Mini·Max 구조의 처리시간 비교
- [ ] 복원 실패 사례와 입력 밝기에 따른 품질 차이 분석
- [ ] Colab의 실제 학습·검증 소요시간을 확인하고 증류 실험 범위 결정

Mini·Max·Max+ 일반 학습은 독립적으로 진행합니다. Max+ 일반 학습이 완료되면 이를 고정된 기본 교사로 Mini 증류를 진행합니다. 발표 전까지 완료 가능한 범위는 실제 학습 시간으로 판단하며, 외부 교사를 포함한 8개 구성 전체 비교는 후속 단계입니다. 무료 GPU의 할당이나 완료 시간을 미리 보장하지 않습니다.

## 2. 확인하려는 문제와 필요한 증거

| 확인할 질문 | 필요한 증거 | 이번 주 확인 범위 |
|---|---|---|
| 현재 베이스라인에 어떤 복원 오류가 남는가? | 정답 대비 PSNR·SSIM, 같은 영역을 확대한 비교 이미지 | 필수 |
| 작은 모델을 쓰면 CPU 시간을 충분히 절약하는가? | 같은 입력·실행 설정에서 Mini·Max 시간 비교 | 필수 |
| 입력 밝기로 복원하기 어려운 사진을 구분할 수 있는가? | 밝기와 복원 품질의 관계, 밝기 그룹별 결과 | 필수 |
| 어떤 사진은 작은 모델로도 비슷하게 복원할 수 있는가? | 학습된 Mini·Max의 사진별 품질 차이 | Mini 학습 완료 시 |
| 증류가 같은 Mini의 일반 학습보다 유리한가? | 같은 조건으로 학습한 두 모델의 검증 성능 | 실제 학습 예산 내 가능 시 |

**해석 범위를 지키겠습니다.** 베이스라인 한 개에서 사진별 성능이 다르다는 사실만으로 모델 선택의 효과가 입증되지는 않습니다. 학습 전 Mini는 속도 측정에만 사용하고, 화질 비교에는 사용하지 않습니다. 현재 체크포인트가 짧게 학습된 결과라면 관찰한 오류를 초경량 구조 자체의 한계로 단정하지 않습니다.

## 3. 역할 분담표

팀장 포함 총 5명입니다. 각 작업에는 주담당자 한 명을 두고, 협업이 필요한 부분은 결과 파일을 전달하는 방식으로 연결하겠습니다.

| 역할 | 담당자 | 주담당 업무 | 발표 자료 담당 |
|---|---|---|---|
| 팀장 | 김경서 | 일정 관리, 실험 범위 결정, 결과 통합, 시연 준비, 발표 진행 제안 | 1~2장, 8장 및 전체 통합 |
| 팀원 A | 이름 기입 | 데이터·평가 기준 고정, 베이스라인 정량 평가, 공통 평가 코드 | 3장, 4장 정량 결과 |
| 팀원 B | 이름 기입 | CPU 추론시간 측정, 학습시간 측정 지원, 속도 차이 분석 | 5장 |
| 팀원 C | 이름 기입 | 밝기별 분석, 실패 유형 분류, 비교 이미지 제작 | 4장 비교 이미지, 6장 |
| 팀원 D | 이름 기입 | 일반 학습 3종 실행 관리, Mini←Max+ 증류, 동일 조건 비교 | 7장 |

### 팀장: 일정·통합·시연·발표

**맡을 작업**

1. 첫날 일반 학습 3종의 실행 담당자와 공통 기준을 확정하고, 작업 상황과 막힌 부분을 확인합니다.
2. A가 정리한 평가 기준을 공유하고, B·D의 학습시간 측정을 바탕으로 이번 주 실험 범위를 확정합니다.
3. 각 담당자가 만든 결과와 해석을 취합해, 직접 확인한 사실과 아직 가설인 내용을 구분합니다.
4. 기존 추론 스크립트로 사진 한 장을 보정하는 짧은 시연을 준비합니다. 시연용 사진과 정답이 있다면 함께 비교합니다. 현장 실행이 불안정하면 녹화본을 준비합니다.
5. 프로젝트 요약 1~2장과 마지막 진행 상황·후속 계획 슬라이드를 작성합니다.
6. 각자 만든 슬라이드 초안을 통합하고, 발표 대본과 예상 질문을 정리합니다.

**산출물**: 통합 PPT, 시연 또는 녹화본, 발표 대본, 예상 질문·답변 메모

**완료 기준**: 모든 결과에 데이터·모델·실행 조건을 표시하고, 발표자가 결과의 의미와 한계를 설명할 수 있는 상태

### 팀원 A: 데이터·평가 기준 및 베이스라인 정량 평가

**맡을 작업**

1. 이번 기준 모델은 새로 학습한 Max(LOL-v2-real)의 best.pt입니다. run.json·log.csv·summary.json으로 설정과 실제 학습량을 확인합니다. 이전 LOL-v1 결과를 이번 기준 점수로 사용하지 않습니다.
2. 저장소의 고정 manifest(train 620 / validation 69 / test 100)를 사용합니다. 중간발표의 품질 분석·사례 선택·설정 비교는 검증 69쌍으로만 수행하고 시험셋은 열지 않습니다.
3. 이미 구현된 evaluation.py를 공통 평가 코드로 사용합니다. 각 학습 폴더의 best_validation_per_image.json에 검증 이미지별 PSNR·SSIM이 저장되므로 이를 C·D와 공유합니다. 평가 코드를 새로 만들 필요는 없습니다.
4. 입력 크기, 전처리, 출력값 범위·클리핑, 지표의 채널 처리 방식을 문서로 남깁니다.
5. 검증 69쌍 전체의 저장된 결과와 평균을 확인합니다. 같은 가중치를 다시 평가해야 할 때만 공통 평가 코드를 실행합니다. 일부 좋은 사진만 골라 평균을 보고하지 않습니다.
6. Mini·Max·Max+의 이미지별 결과를 name으로 연결하고 전체 평균, 검증 이미지 수 69, checkpoint 정보를 정리합니다. CSV가 필요하면 저장된 JSON에서 변환합니다.

**산출물**

- `experiment_settings.md`: 데이터·모델·전처리·평가 설정
- `split_manifest.csv`: 이미지 ID와 학습·검증·시험 구분
- `baseline_quality.csv`: 이미지별 베이스라인 품질
- 전체 평균 PSNR·SSIM 표와 3장·4장 정량 결과 초안

**결과 필드**: `image_id`, `split`, `model_id`, `checkpoint_id`, `width`, `height`, `psnr_db`, `ssim`

**완료 기준**: 다른 팀원이 같은 가중치와 설정으로 평가를 실행할 수 있고, C가 이미지 ID로 결과를 연결할 수 있는 상태

**협업**: 1일차에 설정과 이미지 목록을 전원에게 전달하고, 2~3일차에 품질 CSV를 C와 팀장에게 전달합니다. D에게는 검증용 평가 함수를 공유합니다.

### 팀원 B: CPU 실행시간 및 계산 예산 측정

**맡을 작업**

1. 합의된 목표 기기 Apple M5(10코어) MacBook Pro에서 측정합니다. 기기가 달라지면 별도 결과로 구분하고 CPU 기종·메모리·라이브러리 버전을 기록합니다.
2. 같은 600×400 입력, batch 1, FP32, CPU 1스레드로 Mini·Max·Max+ 시간을 비교합니다.
3. Mini가 아직 학습되지 않았다면 결과에 `Mini 구조 / 학습 전 / 속도 측정용`이라고 표시합니다.
4. 측정 규약에 따라 준비 실행 10회, 측정 100회를 수행합니다. 평균·중앙값·p95와 변동을 기록합니다.
5. model 시간과 end_to_end 시간을 구분합니다. 현재 end_to_end는 PNG 디코드→텐서 변환→forward→clamp→uint8 변환이며 디스크 저장·화면 표시·모델 로딩은 제외합니다. 선택 시스템에서는 상태 계산·선택 비용도 포함합니다.
6. 여유가 있으면 입력 크기를 바꿔 같은 속도 비교를 반복합니다. 해상도가 다른 결과는 조건별로 나눠 표시합니다.
7. D의 Colab 실행 점검에서 학습·검증 시간을 확인합니다. GPU 종류를 기록하고 교사 추론이 포함된 증류 시간은 별도로 측정합니다. 서버 CPU 수치를 목표 M5 결과로 사용하지 않습니다.

**산출물**

- `cpu_latency.csv`: 반복 측정 원자료와 측정 조건
- Mini·Max·Max+ 처리시간 비교 그래프
- `training_budget.md`: 시험 학습 시간, 전체 소요시간 추정, 가능한 실험 범위
- 5장 초안

**결과 필드**: `model_id`, `checkpoint_status`, `width`, `height`, `threads`, `repeat_id`, `inference_ms`, `total_ms`

**완료 기준**: 어떤 조건의 시간을 비교했는지 명확하고, 작은 모델을 선택해 절약할 시간의 크기를 설명할 수 있는 상태

**협업**: 첫날 D와 학습시간을 확인합니다. 성능 측정 중에는 같은 컴퓨터에서 학습이나 다른 무거운 작업을 실행하지 않도록 일정을 공유합니다.

### 팀원 C: 실패 사례와 사진 상태별 품질 분석

**맡을 작업**

1. 입력 사진의 평균 밝기와 어두운 픽셀 비율을 계산하고 계산 기준을 기록합니다. 밝기는 보정 결과가 아닌 입력 사진에서 구합니다.
2. 검증 69쌍만 대상으로 각 모델의 best_validation_per_image.json을 name으로 연결해 밝기·PSNR 관계를 그립니다. 학습·시험 이미지를 섞지 않습니다.
3. 입력 밝기 기준으로 세 그룹 정도를 만들고 그룹별 이미지 수와 평균 PSNR·SSIM을 비교합니다. 그룹 기준도 표시합니다.
4. 전체 평가 결과에서 좋은 사례·중간 사례·실패 사례를 선정합니다. 선정 이유를 적습니다.
5. 각 사례의 입력·베이스라인·정답을 같은 위치로 확대해 비교합니다. 추가 보정이나 사진마다 다른 표시 조건을 적용하지 않습니다.
6. 실제로 관찰한 오류를 분류합니다. 예를 들어 어두운 영역 잔존, 색 왜곡, 세부 무늬 손실 등이 해당합니다. 관찰하지 않은 오류는 결과처럼 적지 않습니다.
7. Mini 학습이 완료되면 사진별 `Max PSNR - Mini PSNR`을 계산하고, 작은 모델로도 품질이 가까운 사진이 있는지 분석합니다.

**산출물**

- `brightness_analysis.csv`: 이미지별 입력 특성과 품질을 연결한 표
- 밝기·PSNR 산점도와 그룹별 요약표
- 대표 사례 비교 이미지 3세트와 관찰 내용
- 4장 시각 자료와 6장 초안

**완료 기준**: 사진 상태와 오류의 관계를 실제 결과로 설명하고, 관계가 약하거나 표본이 적은 경우도 그대로 제시할 수 있는 상태

**협업**: 첫날에는 입력 특징 계산부터 진행하고, A의 CSV가 나오면 연결합니다. 비교 이미지는 A와 함께 4장에 배치하고 팀장에게 선정 이유를 전달합니다.

### 팀원 D: Mini 학습 및 지식 증류 예비실험

**맡을 작업**

1. Mini·Max·Max+ 일반 학습 노트북을 각 실행 담당자에게 배정합니다. 각 모델은 새 초기값으로 독립적으로 학습하며 initial.pt를 보존합니다. D는 Mini 일반 학습과 이후 Mini 증류 비교를 중심으로 진행합니다.
2. 세 모델 모두 random 180×180 패치를 사용합니다. 128×128은 현재 다중 스케일 MS-SSIM 손실에 맞지 않습니다. 먼저 노트북의 2배치 학습+검증 69쌍 점검을 실행하고 B와 실제 소요시간·메모리를 확인합니다.
3. 본 학습은 기본 10 epoch씩 나눠 실행하고, 매 epoch 저장된 progress.json을 확인합니다. 이어갈 때 총 EPOCHS=120과 실험 이름을 바꾸지 않습니다. 두 조건을 발표 전까지 비교할 수 있는지 판단하고, 학습 데이터 수·학습 횟수·완료 예상시간을 첫날 팀장에게 전달합니다.
4. 가능하면 같은 Mini에 대해 일반 학습과 증류 학습을 진행합니다. 학생은 일반 학습의 initial.pt를 --init-checkpoint로 불러와 시작하고 데이터·학습량·평가 방법을 동일하게 맞춥니다.
5. 기본 교사는 이번 random 조건으로 일반 학습한 Max+의 best.pt입니다. Max를 임시 교사로 추가하지 않습니다. Max+ 완료 전에는 일반 학습 결과 분석과 증류 코드 준비를 진행합니다.
6. 교사는 고정하고 같은 random 입력 패치를 교사와 학생에 전달합니다. 기본 교사는 현재 온라인 추론 경로를 사용합니다. 고정 center 패치의 교사 출력을 random 학습에 재사용하지 않습니다.
7. 증류 가중치 β는 제한된 예비 설정으로 정하고 기록합니다. 이번 주에는 많은 조합을 탐색하지 않습니다.
8. 학습 손실과 검증 PSNR·SSIM을 저장합니다. 두 조건의 학습량이 다르면 같은 단계끼리 비교하고, 미완료 결과임을 표시합니다.

**산출물**

- 일반 학습·증류를 실행할 수 있는 코드와 설정
- `training_history.csv`: 조건별 학습 단계와 손실·검증 지표
- 비교가 완료되면 `distillation_comparison.csv`와 가중치
- 학습 곡선, 검증 결과, 7장 초안

**완료 기준**: 두 조건의 차이와 실제 진행한 학습량을 설명할 수 있고, 비교가 미완료라면 그 상태와 필요한 추가 시간을 명확히 남기는 것

**시간이 부족할 때의 대체 산출물**: 실행 코드, 실제 Colab 학습시간 측정, 현재까지의 손실·검증 곡선, 완료하지 못한 비교와 후속 계획. 충분한 비교 없이 증류 성능이 개선됐다고 결론 내리지 않습니다.

**협업**: 첫날 B와 계산 예산을 결정하고, A의 공통 평가 함수를 사용합니다. 사용 가능한 Mini 체크포인트가 나오면 A·C에게 전달합니다.

## 4. 작업 연결과 공통 규칙

### 결과 전달 순서

1. **A가 데이터 목록·이미지 ID·평가 기준을 공유합니다.**
2. **B와 D가 실제 Colab 학습 가능 범위를 확인합니다.** 이 결과로 팀장과 D가 학습 범위를 확정합니다.
3. A는 정량 평가, B는 속도 측정, C는 입력 특징·사례 분석을 진행합니다. D는 합의한 범위의 학습을 진행합니다.
4. C는 A의 품질 CSV를 연결해 분석합니다. D의 모델이 나오면 A·C가 같은 방식으로 추가 평가합니다.
5. 각자 결과 슬라이드와 설명을 작성하고 팀장이 통합합니다.

### 비교와 해석 기준

- 설정을 바꾸면 변경 사항을 기록하고, 서로 다른 조건의 숫자를 같은 조건처럼 비교하지 않습니다.
- 시험 데이터는 최종 확인에 사용합니다. 학습 설정이나 모델 선택 기준을 정할 때는 검증 데이터를 사용합니다.
- 이번 실험은 LOL-v2-real로 고정합니다. 기존 LOL-v1 재현 점수는 과거 기록으로만 제시하고 이번 검증 결과와 직접 비교하지 않습니다.
- 규칙 기반 선택기를 사용하고 620/69/100 분할을 유지합니다. 검증 69쌍(29개 장면)을 모델·설정·임계값 선택에 함께 사용하는 한계를 기록하고 설정 탐색을 제한합니다. MLP 도입은 별도 분할·재학습 필요성을 검토할 확장 과제이며 Oracle는 제외합니다.
- 평가 이미지가 적으면 실제 표본 수를 표시하고 관찰 범위 안에서 해석합니다.
- 밝기와 성능의 관계가 약하거나 Mini·Max 시간 차이가 작아도 중요한 관찰 결과로 기록합니다.
- 메모리는 이번 주 후순위로 두고, 파라미터 수만으로 실제 실행 메모리가 줄었다고 주장하지 않습니다.
- 모델 선택 효과를 나중에 평가할 때는 선택 비용을 포함한 전체 시간과 고정 모델의 시간을 비교합니다.

## 5. 1주일 일정

발표일의 정확한 날짜는 확정 후 기입하고, 아래 일정은 준비 시작일을 1일차로 계산합니다.

| 시점 | 공동 목표 | 담당별 완료 항목 |
|---|---|---|
| **1일차** | 기준·역할 확정, 학습 예산 판단 | A: 설정·목록·평가 코드 공유 / B·D: Colab 실행 점검과 시간 추정 / C: 입력 특징 계산 / 팀장: 역할 확정·PPT 틀 |
| **2~3일차** | 필수 중간 결과 확보 | A: 베이스라인 전체 평가 / B: CPU 속도 비교 / C: 실패 사례·밝기 분석 / D: 가능한 범위의 학습 / 팀장: 시연 준비 |
| **4~5일차** | 추가 비교 및 초안 제출 | D 결과가 있으면 A·C가 추가 평가·분석. 각 담당자는 결과·그림·해석과 슬라이드 초안을 5일차까지 제출 |
| **6일차** | 결과 확정·PPT 통합 | 팀장 취합, 전원 수치·해석 확인, 꼭 필요한 보완 측정만 진행 |
| **7일차** | 발표 연습·질의응답 | 발표 리허설, 시연 확인, 담당별 예상 질문 검토 |

**학습 진행 판단은 첫날, 최종 결과 확정은 6일차에 하겠습니다.** 학습이 길어져 필수 평가와 발표 준비가 밀리지 않도록 범위를 조정합니다.

## 6. PPT 구성과 담당

아래는 8~10분 발표를 가정한 8장 구성입니다. 발표시간이 다르면 분량을 조정하겠습니다.

| 장 | 내용 | 담당 | 넣을 자료 |
|---|---|---|---|
| **1** | 프로젝트 개요 | 팀장 | 입력·보정 사진, 로컬 복원 목적, 품질·처리시간 목표 |
| **2** | 제안 방법과 현재 진행 상황 | 팀장 | 학습 단계의 증류, 실행 단계의 모델 선택, 완료·진행·예정 구분 |
| **3** | 검증 질문과 실험 조건 | A | 데이터·표본 수·가중치·입력 크기·평가 방법. CPU 조건은 B에게 전달받아 반영 |
| **4** | 베이스라인 복원 결과 | A·C | 전체 평균 성능, 대표 사례와 실패 영역 확대 이미지 |
| **5** | CPU 처리시간 비교 | B | Mini·Max·Max+ 반복 측정 그래프, 입력 크기·스레드·학습 전 Mini 표시 |
| **6** | 사진 상태별 복원 품질 | C | 밝기·품질 산점도, 그룹별 결과. 가능하면 Mini·Max 사진별 품질 차이 |
| **7** | 증류 예비실험과 진행 상황 | D | 같은 학습량의 검증 비교 또는 실제 진행한 학습량·시간·현재 결과 |
| **8** | 확인한 내용과 다음 실험 | 팀장 | 확인한 사실, 아직 미검증인 가설, 다음 단계의 우선순위 |

슬라이드는 각자 담당 결과를 초안으로 만들고 팀장이 통합합니다. 자세한 설정과 추가 사례는 필요하면 부록에 둡니다.

발표 설명은 관찰한 범위에 맞춥니다.

- **직접 확인한 결과**: “이번 평가 데이터에서 해당 오류를 관찰했다.”
- **예비실험 결과**: “제한된 데이터와 학습량에서 다음 경향을 확인했다.”
- **아직 남은 질문**: “사진별 모델 선택이 실제로 유리한지는 학습된 모델 간 비교가 필요하다.”
- **외부 수치**: “원 논문의 해당 장치·데이터에서 보고한 결과다.”
